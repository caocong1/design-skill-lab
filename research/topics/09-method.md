# 09 方法论：从需求到交接

> 元数据：更新于 2026-09-27 · 依据：ooux-orca、change-aversion、impeccable、anthropic-frontend-design-skill、anthropic-design-skills、emil-kowalski-skills、taste-skill、design-md-spec、ui-ux-pro-max；现场证据：2026-09-23 实验室页面自用、2026-09-24 两个宿主项目复盘（15 条反馈）；arXiv 2607.22928 · 复核期限：2026-12-26（首轮评测出结果后提前重写）

本篇是 0.8.0 `design-studio` 契约背后的理由层，讲一个会设计的 agent 应该怎样工作、每一步凭什么、证据有多硬、哪里可能是错的。规则本身只在 skill 里写一次，这里不重复条文。

## 当前结论

1. **角色边界：套件是设计师，实现者负责搭建。** 设计师的活是做决定、出图、写规格、交接，最后凭截图验收；实现者在目标技术栈里把东西做出来。作图媒介始终是 HTML / CSS / SVG，渲染成 PNG 来看。生图是一条可选的草图 / 位图通道，必须记录出处，HTML 仍然是交付契约。目标平台只影响三样东西：画框、惯例、约束。方法和质量标准不随平台变。（实测：0.3.0 的纠正；业内对照：其余同类都是前端代码生成器，见 topic 02）
2. **失败模式是回归均值，不是不会设计。** 采样参数固定时，多样性只能来自流程：先写事实文件，再定具体参照，命名车辙，掷骰，隔离生成，最后并排比较。（一手资料：anthropic-design-skills 事实 26–28、impeccable 事实 9）
3. **事实按寿命分三处存放。**
   - `PRODUCT.md`：受众、目的、约束、语气、用户规模、各角色的使用频率，很少变。
   - `DESIGN.md`：视觉系统。如果是新建一套视觉世界，建成之后按成品来写。
   - `surfaces/<surface>.md`：这个界面的访客模式，加一份约 150 字的方向契约。

   本轮 brief 只放四样东西：design read、一句具体参照、一句物理场景、各项假设。（一手资料：impeccable 事实 5、6、15，design-md-spec 事实 16–18；实测：v1 的 brief 混写，导致每轮都要重新问一遍）
4. **流程多重由需求决定，分三档，做之前说明用哪一档。**
   - `quick`：读 → 画 → 渲染 → 底线检查 → 交付。
   - `standard`：在 quick 基础上加参考、系统切片、新鲜评审。
   - `deep`：完整 12 步。

   （业内共识：Emil improve-animations 也分三档；旧分析 10 的"形态选择"梯子由此落地）
5. **deep 档用一套发散引擎对抗第一个念头，不相信模型的第一想法。** 顺序是：命名车辙（这个品类总是做成的样子、它可预期的反面、脑子里冒出的第一个样子，三者都当作已经用掉）→ 列 7 个参照，至少跨 3 个材料族 → `seed.py` 决定哪个方向领头 → 每个方向交给一个隔离的子代理 → 并排的方案板 → 缩略图测试 → 给出推荐，并写明什么情况会让我改变看法 → 保留经典出口。（一手资料 + 实测）
6. **重设计从功能地图出发，不从现有屏幕出发。** 按 ORCA 的顺序拆：对象、关系、行动召唤（CTA）、属性。对象排序决定导航候选，关系决定上下文链接，CTA 挂在它所作用的对象上，属性排序决定卡片和详情的内容顺序，元数据决定排序与筛选控件。先验证对象集合，再画流程。（一手资料：ooux-orca；证据强度：从业者方法，没有独立评估）
7. **变更成本是反向约束：结构可以改，但每处改动都要能说清为什么、谁来付代价、怎样过渡。** 日常高频工具的熟练用户，改动代价最高。重构方向必须写出触发条件，"看起来旧""想要新鲜感"都不算。熟练用户赖以工作的东西，列进"不许悄悄改变"清单。（一手资料：change-aversion；证据强度：Google 的案例没有公布数据）
8. **评审必须由新鲜上下文来做，分两轨，底线过了之后还要拔高。**
   - 评审者只拿到 brief、界面契约、截图清单和测量事实，看不到作者的推理。
   - 先做判断，再看机械证据；先求覆盖，再做筛选。
   - 每条发现标严重度和证据基础。
   - 底线检查通过后，单独做一轮"拔高"：把 brief 里那个值得记住的点再推一步。

   （一手资料 + 现场：作者自评不可信）
9. **验证有上限：一轮批量截图 → 一批修复 → 最多一轮确认，剩下的如实披露。** 截图本身先要站得住：动效已停、从页面顶部截、每张都打开看、带构建标记、断言最终 URL。（一手资料：impeccable 事实 17；现场：宿主复盘）
10. **交接不是描述设计，而是三件事：画出来、给执行者一份可执行的计划、凭截图验收。** 验收时每处偏差归为三类之一：实现缺陷、规格缺口、平台差异。截图是目标，不是素材。（一手资料：emil-kowalski-skills 事实 11；现场）
11. **能算的不估，能机械检查的不靠自觉。但检测干净只说明"已知问题不在"，不说明设计好。**（一手资料：impeccable 事实 29 "A clean detector run is evidence, not proof"）
12. **只有评测能告诉我们"更好"是否成立。** 单次事故先记进 casebook，出现两次独立的同类事故才升级为规则。截至 2026-09-27，评测框架已经建好，还没有跑过一轮，下面列的可证伪条件全部还没有结果。（实测）

## 论证

### 1. 角色边界的来历：一次纠正，三个根因

0.3.0 之前，用户问过一句"Flutter、Tauri、鸿蒙、小程序、原生桌面怎么办"。agent 的第一反应是去打通各技术栈的渲染和测试工具，已经开始写 Flutter golden test 的脚手架。用户叫停，反问："你的核心是设计，为什么会被前端技术局限？"事后归纳出三个根因：

- **把作图媒介当成了目标平台。** Web 是唯一一个两者重合的平台，这个巧合掩盖了二者的区别。
- **把设计师的活滑成了实现者的活。** 在目标栈里搭出来并验证，是 coding agent 的职业本能。
- **继承了同类项目的框架。** 当时调研的同类项目全是前端代码生成器，"设计 = 生成前端代码"的前提就这样带了进来。可用户最初给的 15 个站点，全是设计师用的资源。

用户随后补了关键一句：HTML / CSS 本来就是各前端通用的语言，设计出 Web 形态的界面，coding agent 有能力把它转成对应平台的页面；针对某个技术栈的精确指导只是优化项。由此落地了几样东西：

- 各平台的样机框；
- 可移植样机规则：按目标的逻辑尺寸作画，只用可移植的 HTML / CSS 子集，组件和状态在标记里具名，区分系统组件和自绘组件；
- 交接包；
- `implement-design` 改为写给实现者的指南。

同一个根因后来又出现了一次。v1 的 `implement-design` 描述里写着 "UI polish in an existing project"，于是一句"优化一下 UI"可能直接落到实现者那条路径上，而那条路径天生不做重设计，正好会重演 0.7.0 纠正过的"只抠细节"。0.8.0 把它的触发条件收窄为"已经有设计 / 交接 / 样机，要在栈 X 里做出来"，不再覆盖"UI 优化""切图""标注"。

证据状态：在同类里独有（全面审计 2026-09-27 的机制对照：没有其他项目在设计阶段处理原生或国内平台）。但"样机转成原生界面后是否保真"从来没测过。评测 brief 03（iOS）和 04（小程序）测的是设计质量，不是转译质量。

### 2. 循环（deep）与每一步的理由

| 步 | 做什么 | 为什么 | 证据 |
| --- | --- | --- | --- |
| 1 | 检查宿主 | 宿主已有 `DESIGN.md` 或 token 文件时，它们就是唯一的系统记录，原地更新，不另起一套 | 现场：两个宿主之一 |
| 2 | 写事实文件 | 已经定下的事不再重问；方向契约要能被拿去对照 | impeccable |
| 3 | 参考研究：截图 → contact sheet → 看过再解构 | v1 的这一步在实际执行中退化成读 HTML 文字，或者干脆凭模型先验 | 审计 + topic 01 |
| 4 | 发散 | 见第 3 节 | impeccable、anthropic-design-skills |

| 6 | 系统：`DESIGN.md` + tokens，写入时 lint，改动时 diff | 哪怕只做一页，也隐含字号阶梯、色彩角色这些决定 | design-md-spec |

### 3. 发散引擎：为什么必须靠流程

- **采样参数调不了。** Sonnet 5 对非默认 `temperature` 直接返回 400，官方推荐的多样性手段就是先出选项（anthropic-design-skills 事实 27）。
- **模型模拟不了随机。** gpt-taste 让模型在计划里"模拟一次 Python 随机"，用提示词的字符数当种子（taste-skill 事实 23）。这恰好说明需要一个真脚本。Impeccable 的骰子更进一步：从模型自己按共鸣度排好的候选里抽第 3 到第 N 个，从不抽前两个（impeccable 事实 9）。
- **同一个上下文里连续生成的方向会互相靠拢。** v1 为此不得不加缩略图测试。0.8.0 改为每个方向交给一个子代理，它只拿到 brief、这个方向在各轴上的坐标和参照，看不到别的方向。
- **车辙要命名三次。** 品类总是做成的样子、它可预期的反面、脑子里第一个冒出来的样子，都算已经用掉（impeccable 事实 8、14 的"第一套配色视为已花掉"）。
- **参照至少跨 3 个材料族。** brief 里字面上的比喻最多只能占一个候选名额。
- **轴分视觉和结构两类。** 视觉轴：字体气质、色彩策略、版式语法、密度、形状、层次、图像、动效。产品界面还要有结构轴：导航模式、任务容器、数据呈现、流程形态。
- **方案板用并排的独立画框。** v1 说"一套 DOM 加实时切换器是最强的方案板"，而一套 DOM 加作用域 token，本质上就是换皮的机器，和结构轴的要求自相矛盾，0.8.0 删掉了这句。
- **每张方向卡都要写"它会在哪里失败"。** 缩略图缩小后如果分不清，就说明是同一个方向。实验室页面的 10 张缩略图一眼可辨，差异来自版式和字体，不只是颜色（2026-09-23 自用记录）。
- **经典出口**把"熟悉"留成用户可以做的选择，同时不允许模型把它当默认值。
- **"一个都不行"说明轴选错了**，要回去换轴，而不是在原轴上再加一个方向。

证据状态：机制都来自同类项目，本套件没有测过掷骰和子代理隔离能不能提高产出的多样性与质量。对应的是下文可证伪条件 F1。

### 4. 从功能地图重设计，加上变更成本的反向约束

**0.7.0 的来历。** 维护者在两个宿主项目上用套件做整体 UI 优化和多主题：一个是带 Office / WPS 加载项的 Web 业务系统，一个是 AI 助手 Web 应用。两次结果都很保守，两份 `decisions.md` 的开头分别写着"结构不动""风险最低"，多主题也只换了配色。原因在 skill 自身：方向的差异轴全是视觉轴；redesign 先看旧界面再出方向；"保留有效部分""现有系统是约束"这类措辞把 agent 推向保守。0.7.0 改为先做功能拆解，再脱离旧界面出方向，要求至少两个重构方向，细节修复作为所有方向共享的基线。

**0.7.0 缺的是方法依据。** 证据层审计指出，这条最重要的新规只凭一次纠正，没有任何文献。0.8.0 用 ORCA 补上（ooux-orca）：

- 对象是用户心智里的名词。用 SIP 测试判断：有没有结构（属性）、能不能举出实例、对用户和业务是否重要。日历、地图、目录、库这类集合名词是视图，不是对象。
- 关系用对象 × 对象矩阵记录，含基数。它铺出导航路径。
- CTA 用角色 × 对象矩阵记录，受权限和对象状态约束，挂在它作用的对象上。
- 属性分核心内容和元数据，强制排序；排序代表优先级，不代表屏幕位置。
- 名词的来源是路由、API、数据模型、文档、界面标签、搜索和客服日志，**不是截图**。
- 呈现阶段只用四种原语：卡片、详情、列表、落地页。
- 对象层面的四种失败：变形（同一对象换个场景就换一副样子）、伪装（不同对象共用同一种外观）、拆散（一个对象的数据和操作散在各处）、孤立（对象之间没有连接）。

证据强度要说清楚：这是一套公开的、可以逐步照做的从业者方法；CNN 和 GTRI 的案例是作者自己的报告，没有找到独立评估。

**反向约束**（change-aversion）：

- 设计团队看自己界面的时间以千小时计，用户每次访问只有 2 到 3 分钟。日常用户靠的是熟练、自动化的操作，所以同样偏爱熟悉的设计。默认原则是"先做对，再慢慢改"（Nielsen 2009）。
- 推倒重来只有两种正当理由：几乎没有现有用户；或者界面经过多年修补，已经失去统一的概念结构（Office 2007 是例子）。Loranger（2015）补充了几个触发条件：渐进改进已经榨干；技术阻塞了关键路径；架构一团乱；全站转化率极低；对标下来远不如竞品。
- 变更的风险从低到高依次是：基础设施、功能、业务、界面。重组信息架构风险最高。
- Spool 的反驳很有用：用户讨厌的是"变更的体验很糟"，不是变更本身；熟练用户会"突然变笨"，而且多数人会怪自己。

**两者并不矛盾。** "质疑结构"管的是分析：从功能地图推导，不从旧屏幕出发。"变更成本"管的是决定：每一处结构改动都要能拿出理由。方案板因此固定为：一个演进方向，加至少两个重构方向；每个重构方向写明触发条件，并附一行成本说明（动了什么、影响谁、用什么帮助过渡）。

**"不许悄悄改变"的清单**合并两个来源：

- taste §11.F：URL / slug、导航标签、表单字段名和顺序、字标、法务文案、埋点事件名；
- change-aversion：快捷键、高频控件的位置、排序和筛选的默认值、用户自己组织的内容。

**迁移计划**取自 Google 的十步框架，加上 Figma UI3 和 Spotify 的实践：先自愿试用 → 允许切回旧版 → 公布下线日期 → 下线；准备"什么挪到了哪"的对照表；提供可选的标签提示；新版成为默认之前，帮助文档要到位；设反馈渠道，并告诉用户"你说了什么，我们改了什么"；用护栏指标守住"不比旧版差"。Figma UI3 从发布到旧版下线约 10 个月，提前 36 天通知；beta 数据和设计冲突的地方它都改了回去，比如浮动面板改回固定面板，X/Y 仍放在 W/H 上面。

证据强度：Google CHI '13 只给了结论，没有数字；没有任何对照研究能分离出单项缓解措施的效果。所以这是业内共识级别的约束，不是被测量过的定律。

**旧观点错在哪里。** 0.7.0 有矫枉过正的风险：只写了"放开"，没写"代价"。0.6.0 那句"保守的重设计可以省掉灵感步骤"方向正相反，0.7.0 已经删掉。评测 brief 06 正好同时考两头：保留旧结构的换皮，Fit 和 Hierarchy 最高只能得 3 分；悄悄删掉功能要扣分；诊所经理关心的熟悉锚点（按医生分列的日视图、各个操作的名称）要么保留，要么替代方案明显更容易用。

### 5. 新鲜评审与拔高

**为什么一定要新鲜上下文：**

- 作者会高估自己的产出。实验室页面那一轮，评审者就是作者本人，已被记为局限（2026-09-23 自用记录）。
- Design Theater 测到，超过 25% 的设计理由没有体现在界面上。
- Impeccable 的原话是："Models systematically believe their HTML, CSS, and SVG recreation of an image succeeded when it did not."

**评审者拿到什么：** brief、界面契约、截图清单、测量事实。清单要逐项列出，不能只给目录通配符：宿主复盘里有个评审子代理只拿到几个通配符，花了约 31 分钟、23 万 token 看了约 110 张截图。评审者拿不到作者的推理过程（skill-creator 的盲评比较器；Impeccable 收尾评审的输入包）。

**评审的顺序和记法：**

- 先判断，再看机械证据，因为检测器的输出会锚定判断（impeccable 事实 22）。
- 先求覆盖，再做筛选：发现阶段把问题全列出来，由单独一步去复核，复核时重读每一处被引用的位置（Sonnet 5 指南；Emil improve-animations 的复核步骤）。
- 每条发现记严重度 P0–P3 和证据基础：已证实 / 需人确认 / 必须由人判断。
- 处置结论只有四种：ship / fix / rebuild / recapture。无人值守时最多两轮。单上下文的降级运行必须写明。
- 已经发出的发现，事后不改写；有意偏离写进 `decisions.md`（宿主复盘）。
- 报告行格式用 Before | After | Why（emil-kowalski-skills 事实 7）。

**评分表：** 二元的底线检查，加 1–5 分的上限评分，每个分数档都要有锚点描述。门槛是各维度都 ≥ 3，Fit / Hierarchy / Identity ≥ 4。原因是 v1 的门槛是"低于 2 分必须修"，而 2 分的定义正是"能用但平庸"，平庸按定义就能通过；v1 的锚点也只写到 1 分和 3 分。

**拔高：** 底线检查过了之后，找出 brief 里那一个值得被记住的想法，做两个加强版，由新鲜评审挑一个。这一步没有测量依据，有一个已知的风险：拔高容易变成往上堆装饰。canvas-design 的"只精修，不添加"可以作对照。

### 6. 有界验证

截图站不住，结论就站不住。现场记录下来的截图陷阱有：

- 无头 Chrome 会继承系统的深色模式；
- 窗口宽度最小 500 px（全面审计在 Chrome 153 上复核过）；
- 对禁止被 iframe 嵌入的站点，小于 500 宽的截图会静默拍到错误页，退出码却是 0；
- 路由被静默重定向到别的页面；
- 窗格截在"加载中"；
- 前后两组截图宽度不同；
- "之前"截自线上、"之后"截自本地，出现假回归；
- 重拍时拍错了构建。

对应的规则：断言最终 URL 或就绪元素，不用固定等待；前后在同一构建、同一环境下截；视口和倍率写进文件名；每张截图都带构建标记，看图之前先核对。

轮数上限来自 Impeccable：一轮批量（所有视口、主题、状态一起截）→ 一批修复 → 最多一轮确认。v1 的完成定义没有上限，只会引出没完没了的自检。另有一条单独的规则：P0 / P1 问题只有在它自己的证据截图重拍之后才能算修好。宿主复盘里就出过这种事：头号问题在修之前就被标成了"已修复"，结果三个主题下都还在。

### 7. 交接

- **交接包：** 画面 × 状态 × 目标 × 主题的 PNG，按 `<screen>-<state>-<target>-<theme>` 命名；规格说明；`handoff.json`；标明哪些是系统组件、哪些是自绘；授权信息随素材一起交。
- **给执行者的计划：** 现有代码逐字引用并标 `file:line`；目标值全部写出；给一个可以模仿的范例；写清边界；按提交号盖章，代码漂移了就停下来报告；机械验证加手感验证；写明完成条件（emil-kowalski-skills 事实 11）。执行者可能是更便宜的模型，计划要写到"零上下文也能照做"。
- **验收由 `critique-design` 统一负责：** 同一逻辑尺寸、主题、状态 → 并排 → 叠图或 diff → 写成"预期 → 实际" → 归为实现缺陷、规格缺口、平台差异之一。v1 里这套流程在 4 个文件里各写了一遍。
- **重设计的交接加一节上线计划：** 分几期、能否切回、下线日期、挪动对照表、满意度与护栏指标（change-aversion）。
- **设计和实现是同一个 agent 时，** 交接缩减为一份验收截图清单（宿主复盘，0.6.0）。

### 8. 评测：知道的唯一办法

v1 的反馈闭环能产出真实的改动：15 条里 11 条落进了文件的具体行。但它的样本是 2 个项目、1 天，其中 11 条是事后从会话记录补录的；影响最大的一次改动（0.7.0）来自维护者本人的纠正；无人值守的 evolve 从没真正跑过。它记录的是轶事，回答不了"0.7.0 是否比 0.6.1 更好"。另一个数字也说明问题：`skills/` 的全部提交累计新增 7,156 行、删除 202 行，每次事故都在往里加规则。0.8.0 用三样东西应对：

- **触发评测：** `evals/triggers.jsonl` 共 100 条提示，其中 design-studio 48 条、critique-design 10 条、implement-design 10 条、none 32 条；中文 57 条、英文 43 条；用代理方法跑。
- **产出评测：** 6 个固定 brief × 3 个臂（不装 skill / 0.7.0 / 0.8.0）；统一渲染；测量事实由编排方算好交给评审；3 位盲评评审各按 1–5 打分并做两两偏好；声明规则预先定好（至少赢 5/6 个 brief，且总均分高 0.5 以上，才能说"更好"）；逐条核对理由与渲染；如实报告成本。
- **诚实规则：** 输了也放在标题里；不因为结果难看就重评；独立评审给套件的分数如果不高于不装 skill，要改的是套件，不是评测。

评测自己也承认偏差：Identity 维度的"与题材无关"判据，两个版本的套件都在教；`lint.mjs` 随 0.8.0 一起分发，0.8.0 的臂可能在设计时就跑过它。casebook 的"两次独立事故才升为规则"是本套件自己定的约定，没有外部证据。

### 2026-09-21 以来改了什么，旧观点错在哪里

- **"入口 + 11 个子 skill"改为 3 个。** 按"工作流是否不同"来拆分，原则本身没错，但拆出来的子 skill 并不能独立安装：v1 的核心 6 个 skill 之间有 40 多处 `../` 相互引用；子 skill 被直接触发时，会绕过只写在路由里的核心流程；触发描述互相重叠。
- **"每个 SKILL.md 一屏半左右"**当时只是意图，实际写到了 157 到 284 行。现在由 gates 按行数预算强制执行。
- **自我违反清单更新：**
  - "从没在真实任务上跑过"已经不对：有实验室页面和两个宿主项目。
  - "没有评测"在第一轮跑完之前仍然成立。
  - "平台参考全靠通识"已经过时：`apple-hig-*`、`material-3-expressive`、`harmonyos-design`、`fluent-2` 已有摘要，见 topic 07。
- **"新眼光评审"从"宿主支持时才做"改为默认用子代理，降级运行时必须写明。**
- **"合适高于出彩"保留。** 评测对工作类工具明写"克制不扣分"。
- **非目标保留：** 不做用户研究，不做品牌战略咨询，不代替商标检索，不承诺易腐规格的时效。只有一条要重审："不驱动 Figma"，因为 Figma MCP 已经可以写画布。

## 未决问题

- 拔高这一步的效果没有测过，可能变成往上堆装饰。
- `options` 要不要增加"在宿主代码里实时切换变体"的形态（Emil prototype），还是只用静态方案板。
- 评测时没有用户在场，套件本该让用户做选择的地方，都变成了 agent 自己选。所以评测系统性地低估了"收敛"这一步的质量。
- 功能地图的成本：单个界面的小改版是否也要做 ORCA？现在的写法是只在 deep 档做。
- 变更成本里的 beta、A/B、护栏指标都是给团队的建议，套件自己无法执行，也无法验证。
- 编辑钩子（在编辑后自动跑 lint）没有采纳。
- "不驱动 Figma"这个非目标，和 Figma MCP 已能写画布的现实之间，要做出取舍。
- 评审和作者是同一个模型家族时，"新鲜"能保证多少独立性，没有测过。

## 对 skill 的约束

- `skills/design-studio/SKILL.md`（≤ 200 行）：
  - 角色与媒介；
  - 模式名一字不改（`full`、`piece`、`options`、`inspire`、`critique`、`redesign`、`handoff`、`implement`）；
  - 三档力度，并要求说明选了哪一档；
  - deep 的 12 步；
  - 有界验证的具体轮数；
  - 操作词；
  - 产出目录；
  - "brief 的原话永远优先"；
  - 任一模式开工前的必读链不超过 3 个文件。
- `references/process/truth-files.md`：
  - `PRODUCT.md` 记录用户规模和各角色的使用频率；
  - 界面契约约 150 字，永远不进入交付代码；
  - 写一句具体参照和一句物理场景；
  - design read 写成一行，只有在理解明显有分歧时才问一个问题。
- `references/process/directions.md`：
  - 车辙三行；7 个参照跨 ≥ 3 个材料族；
  - 子代理只接收 brief、这个方向的轴坐标和参照；
  - 方案板用并排的独立画框；方向卡写"会在哪里失败"；做缩略图测试；保留经典出口；
  - 产品界面方向写明它基于哪种对象排序和哪些关系；
  - 重设计方案板：1 个演进方向，加至少 2 个重构方向，每个重构方向附触发条件和一行成本说明。
- `references/process/redesign.md` 与 `templates/function-map.md`：
  - 先做功能地图，再看现有屏幕；
  - 功能地图包含：对象表（含 SIP、状态、数量）、对象 × 对象矩阵、CTA 矩阵、属性排序、未决问题（每条标"猜错的风险"）、各角色使用频率、重设计触发条件、资产清单；
  - 列出对象层面的四种失败；
  - 细节修复作为所有方向共享的基线；
  - "不许悄悄改变"清单与迁移计划；
  - 注明 ORCA 是从业者方法。
- `references/process/render-and-look.md`：
  - 有界轮数；截图有效性规则；
  - P0 / P1 修复必须重拍证据截图；
  - 报告里写明哪些没有验证。
- `references/process/handoff.md`、`templates/handoff-spec.md`、`templates/handoff.json`、`templates/acceptance-report.md`：
  - 计划的各节，含"漂移即停"；
  - 截图是目标，不是素材；
  - 验收按三类归因；
  - 重设计附上线计划；
  - 写明同一 agent 既设计又实现时的精简做法。
- `references/casebook.md`：只收单次事故，写成"症状 → 原因 → 检查"；出现两次独立的同类事故，才升级为规则。
- `skills/critique-design/SKILL.md`（≤ 150 行）、`references/rubric.md`、`references/heuristics.md`、`templates/critic-brief.md`、`templates/critique-report.md`：
  - 新鲜评审的输入包；先判断后看 lint；先覆盖后筛选；
  - 严重度 × 证据基础；四种处置；最多两轮；
  - 底线 + 上限评分表和门槛；Before | After | Why；
  - `heuristics.md` 加入对象层面的四种失败，以及一条重设计检查："日常用户是否丢了一条学会的路径，却没有替代或指引"，并区分正常的变更抵触（先降后回升）和真正的退化（稳定在基线以下）。
- `skills/implement-design/SKILL.md`：
  - 触发条件收窄，不再覆盖"UI 优化""切图""标注"；
  - P0 / P1 修复必须重拍证据截图。
- `evals/`：F1–F8 各有对应的测量；每一轮的结果写进 `research/field/evals-<date>.md`；输了要在 CHANGELOG 和 README 里写明。
