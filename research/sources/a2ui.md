> 中文导语：A2UI 是 Google 发起的"生成式 UI"协议：智能体不发 HTML/代码，只发一串声明式 JSON，而且只能使用客户端事先登记的"组件目录（catalog）"里的组件，样式完全由宿主自己的设计系统决定。它改变了设计交付物：面向生成式 UI 时，设计师交的是"组件目录 + 语义变体 + 约束"，而不是一张张固定屏幕。AG-UI 是另一层——连接智能体后端与前端的事件协议，常作为 A2UI 的传输管道。

## Key facts
1. **Versions.** Public since 2025-12-15 (v0.8); v0.9 announced 2026-04-17; **v0.9.1 is "Current Production"**; **v1.0 is a release candidate** ("previously v0.10 in draft") (docs/public/specification/v1.0-a2ui.md). Maintained renderers (reference/renderers.md): React, Lit, Angular (all three share `@a2ui/web_core`) and Flutter via the GenUI SDK (`flutter/genui`), each "Stable" for v0.8 and v0.9.1; Jetpack Compose "Alpha" for v0.9.1; SwiftUI "Planned"; v1.0 support "Planned" for all. Python agent SDK `a2ui-agent-sdk`.
2. **Core idea** (v0.9 blog): "a framework-agnostic standard for declaring UI intent … your agent can generate your UI using your existing component catalog on any device"; "Agents can 'speak' UI with your design system". The optional starter set was renamed **"Standard" → "Basic"** because "frontend developers don't want new components".
3. **Security model** (intro blog; a2ui_protocol.md#client-side-logic--validation): declarative data, **no executable code**; the client keeps a catalog of trusted, pre-approved components and the agent may only request those; client-side logic is limited to named registered functions.
4. **Four server→client messages** (v0.9.1): `createSurface` (`surfaceId`, `catalogId`, optional `theme`, `sendDataModel`), `updateComponents` (flat list), `updateDataModel` (JSON Pointer `path` + `value`), `deleteSurface`. Stream is JSONL/frames; ordered delivery required (a2ui_protocol.md#the-transport-contract).
5. **Adjacency-list UI tree** (a2ui_protocol.md#ui-composition-the-adjacency-list-model): components are sent flat with `id` + `component` type and reference children by id; exactly one component has id `root`; nothing renders until `root` arrives, then the client renders progressively and **renders placeholders for children or data not yet received**. Design consequence: every generated surface has visible partial/loading states.
6. **Catalog model** (catalogs.md): a catalog = JSON Schema of components + functions (+ theme in ≤v0.9.1), identified by a `catalogId` URI-like string (need not resolve). Client sends `supportedCatalogIds` in preference order with every message; the agent picks one per surface and it is **locked for the surface's lifetime**; if none matches, "the agent will not send a UI". Recommendation: for a mature frontend "define a catalog that mirrors your existing design system" rather than adapting the Basic catalog. Catalogs can extend or cherry-pick from Basic; inline catalogs sent by the client at runtime are "supported but not recommended in production".
7. **Basic catalog v0.9.1 — 18 components**: Text, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Modal, Divider, Button, TextField, CheckBox, ChoicePicker, Slider, DateTimeInput. Semantic variants (catalog.json): Text `h1–h5 | body | caption`; Image fit `contain | cover | fill | none | scaleDown`, Image variant `icon | avatar | smallFeature | mediumFeature | largeFeature | header`; Button `default | primary | borderless`; TextField `shortText | longText | number | obscured`; ChoicePicker variant `mutuallyExclusive | multipleSelection`, `displayStyle` `checkbox | chips`; Row/Column justify incl. `spaceBetween/Around/Evenly`, align `start|center|end|stretch`; List `vertical | horizontal`; **Icon: 59 named system icons** (e.g. `accountCircle`, `search`, `send`, `warning`).
8. **Basic functions**: validators `required, regex, length, numeric, email`; formatters `formatString` (`${/json/pointer}` interpolation), `formatNumber, formatCurrency, formatDate, pluralize`; `openUrl`; `and, or, not`. Inputs carry `checks` with messages; a Button with failing checks is automatically disabled (a2ui_protocol.md#example-button-validation).
9. **Theme (v0.9.1 Basic)**: the schema defines three properties, `primaryColor` (6-digit hex), `iconUrl`, `agentDisplayName` (with `additionalProperties: true`). The last two give **attribution** ("which sub-agent or tool is responsible for a particular UI surface"); orchestrators should overwrite them with verified identity to prevent impersonation (a2ui_protocol.md#identity-and-attribution).
10. **Styling philosophy** (guides/theming.md): "Agents describe *what* to show; renderers decide *how* it looks." Agents give semantic hints only, never `fontSize`/`color`. Web Basic renderers theme through CSS variables on `:where(:root)` (e.g. `--a2ui-color-primary`, per-component `--a2ui-card-background`, `--a2ui-font-family-title`, `--a2ui-font-family-monospace`); dark mode follows `prefers-color-scheme` or classes `a2ui-light` / `a2ui-dark`. The guide notes Basic components are **not** wired to the agent's `theme`. (The guide's code samples still use v0.8 syntax such as `usageHint`; v0.9.1 uses `variant`.)
11. **v1.0 candidate changes that matter to design** (v1_0 evolution_guide.md): **`theme` and `primaryColor` removed** "to separate layout from branding"; catalogs may be **mixed** within one surface; catalogs gain an `instructions` field for design guidelines and usage rules (replacing an external `rules.txt`); composition constraints `allowedParents` / `allowedChildren` with reserved root type `Surface`; accessibility attributes gain ARIA `live` (`off|polite|assertive`) and `hidden`, and renderers must infer screen-reader semantics from visible text; `Video.posterUrl`, `TextField.placeholder`, `Slider.steps`; `openUrl` requires user activation; "client/server" renamed "renderer/agent"; MIME `application/a2ui+json`.
12. **Validation loop** (a2ui_protocol.md#usage-pattern-the-prompt-generate-validate-loop; catalogs.md#a2ui-schema-validation--fallback): prompt with catalog + examples → generate → validate; errors go back as `VALIDATION_FAILED` with a JSON Pointer path. Renderers must degrade gracefully: unknown component → safe fallback or skip; whole surface fails → text fallback or "This interface could not be displayed."
13. **User actions** return as `action` {`name`, `surfaceId`, `sourceComponentId`, ISO-8601 `timestamp`, `context`}; with `sendDataModel` the full surface data model rides along in transport metadata (supports co-editing with the agent).
14. **Transports**: A2A, AG-UI, MCP (tool output or resource), SSE + JSON-RPC, WebSockets, REST (no streaming) (a2ui_protocol.md#transport-bindings).
15. **A2UI vs MCP Apps** (agent-ui-ecosystem.md; 2026-06-17 blog co-written with MCP Apps co-creators): MCP Apps = pre-built HTML in a sandboxed iframe, remote server controls appearance; A2UI = declarative blueprint, **host app controls styling and inherits its design system**. The blog names iframe costs as "clashing design systems or redundant scrollbars" and offers three patterns: A2UI over MCP servers, an MCP App inside an A2UI component, an A2UI renderer inside an MCP App; "We are considering making a MCP extension to support A2UI".
16. **AG-UI (brief)**: "open, lightweight, event-based protocol" connecting agent backends to user-facing apps; the docs place it beside MCP (agent↔tools) and A2A (agent↔agent). Event families: lifecycle (RunStarted/Finished/Error, steps), text message streaming, tool calls, state snapshot/delta (event-sourced), activity, reasoning, subagents, plus interrupts for human-in-the-loop pause/resume (`outcome: {type: "interrupt"}`). AG-UI states it "is not a generative UI specification" and carries A2UI, MCP-UI/MCP Apps, Open-JSON-UI or custom specs (docs.ag-ui.com/concepts/generative-ui-specs).

## What it changes for the skills
- skills/design-studio/references/disciplines/ai-experience.md: add "generative UI" surface: when an agent composes UI at runtime, the design deliverable is a **component catalog** (components, semantic variants, allowed parent/child, copy rules in `instructions`, validation messages, fallback states) plus a renderer theme, not fixed screens; include agent attribution (name + icon per surface) and progressive/partial states.
- skills/design-studio/references/process/system.md: map DESIGN.md tokens to renderer CSS variables (e.g. `--a2ui-*`); agents never carry visual values — theme lives in the renderer.
- skills/design-studio/references/process/handoff.md: generative-UI handoff = catalog JSON Schema + per-component visual spec + examples for few-shot prompting + graceful-degradation designs.
- skills/design-studio/references/platforms/embedded-hosts.md: decision rule — host-native rendering (A2UI) when the host must keep one design system across agents; iframe (MCP Apps) when the server must own a bespoke UI.
- skills/critique-design/references/heuristics.md: check generated surfaces for missing-root/partial render, unknown-component fallback, disabled-until-valid buttons, attribution present.
