# skill 套件的设计取舍与自评

> 分析版本：1.0 ｜ 最后更新：2026-09-21 ｜ 覆盖来源：本仓库自身（元层文件，非来源分析）｜ 版本见 `analysis/SOURCE_INDEX.md`

这篇记录"为什么套件长成这样"，以及它目前**违反自己规则的地方**。它是一份自评，恰好处在"agent 会自信地夸奖自己的产出"这一失败模式的正中央，应当被当作待复核的材料。

## 为什么是"入口 + 11 个子 skill + 维护 skill"

用户给的范围是：Web 前端、移动与桌面 App、动效、图标、平面设计"等等"；用途是：按需求出完整设计、设计单个页面或组件、针对网站给灵感、同时出几套方案，并要求"像资深设计师一样多想一些用途"。

- **按"工作流是否不同"而不是按"学科名词"拆分。** 多方案（`explore-design-directions`）与找灵感（`find-design-inspiration`）是横切能力，任何学科都会用到，所以独立成 skill 而不是塞进每个学科里重复一遍。
- **产品界面与营销站点分开**：前者被反复操作，清晰与可预期压倒表达；后者是一篇有节奏的论证。把两者写在一起，规则会互相打架（比如"惯例即功能"对"别长得像模板"）。
- **设计系统、评审、落地各自独立**：它们有各自的交付物契约（token 与 DESIGN.md、带证据的问题表、宿主技术栈里的代码与截图证据）。
- **共用的基础知识放在入口 skill 的 `references/` 里**，子 skill 用相对路径引用，不各写一份。
- **每个 `SKILL.md` 控制在一屏半左右**，易腐的细节（平台规格、库 API、尺寸表）下沉到带日期的参考文件。

## 在用户列出的用途之外，补了哪些"资深设计师会做的事"

1. **设计评审与验收**（`critique-design`）：带证据、分级、分"立即可做 / 系统性修复 / 需要重新设计"的中文报告；同时作为套件自身产出的新眼光把关。
2. **重设计的资产盘点**：先问"用户真正认得的是什么"，再决定改多远（刷新 / 演进 / 革新）。
3. **竞品拆解与留白分析**：找出"人人都做的"与"没人做的"。
4. **风格 DNA 提取**：从参考站读出 token 与规则，并强制写"差异化计划"，把学习与抄袭分开。
5. **Token 漂移审计**：在现有代码库里清点散落的颜色、字号、间距，聚类近似值，给出映射表与分步迁移计划——对开发者价值很高、几乎没有同类 skill 覆盖。
6. **状态矩阵**：把空、加载、错误、权限、超长内容、环境差异当作设计对象。
7. **数据密集界面与数据大屏**：后台 CRUD、表格、表单、仪表盘，以及大屏与数字孪生控制台的可读距离、固定画布、反"深蓝发光"套路。
8. **AI 产品界面**：六个问题、会话机制、agent 动作审批。
9. **平台适配**：iOS、Android、HarmonyOS、小程序、桌面（Electron/Tauri）、CLI。
10. **中文排版与字体授权**：禁则、混排、字体栈、Web 字体分包、商用授权风险。
11. **从代码产出平面物料**：海报、社媒图、OG 图、演示文稿、可印刷 PDF，以及"字体没加载"这个经典事故。
12. **授权台账与诚实规则**：不编造客户 Logo、评价、数据；占位必须标注。
13. **趋势雷达**：带日期、区分"时尚"与"转向"。
14. **设计决策记录**（`decisions.md`）：选了什么、否了什么、为什么，避免绕回去。

## 非目标

- 不是用户研究套件：不做访谈、问卷、可用性测试的组织，只在 brief 里要求"成功长什么样"。
- 不做命名与品牌战略咨询：只做一页纸的策略，够评判标志即可。
- 不能替代商标检索与法律意见：skill 明确要求提示用户做专业检索。
- 不驱动 Figma 等设计工具（除非宿主提供了桥接）；媒介是代码。
- 不承诺平台规格、库 API、社媒尺寸的时效：这些文件标注了易腐与复核日期。
- 不做自动化来源摄取：判断什么值得收是这个仓库的全部价值。
- 不是设计作品集：仓库里没有"用这套 skill 做出来的案例"。

## 已知的自我违反

1. **教了"渲染后用新眼光评审"，但这套 skill 自己没有被评测过。** 没有验证集、没有前后对比、没有一次真实任务的运行记录。所有规则的有效性目前都是"合理推断"，不是"已验证"。
2. **教了"只摘要真正抓到的东西"，但多份参考文件主要来自模型的通识而非一手摘要**：`platforms.md`（HIG、Material、HarmonyOS 均未取得正文）、`design-brand-identity`、`design-graphics`、`design-marketing-sites`、`data-dense-ui.md` 的大部分内容。这些文件里的数值已尽量标注"需核对"，但它们的证据等级明显低于 `typography.md`、`motion-tokens.md`、`token-formats.md`。`source-map.md` 如实列出了每个文件的证据等级。
3. **教了成本纪律，但这个仓库的第一次调研恰恰违反了它**：2026-09-20 一次性派出 9 个顶配模型的调研 agent，在写出任何交付物之前耗尽了额度，全部失败；只抢救回草稿（候选域名清单、GitHub 元数据、部分已抓取的原文）。之后改为"主 agent 筛选 + 脚本验链"，100 秒验完 607 个 URL，零模型开销。教训写进了 `iterate-design-lab` 的 Cost Discipline。
4. **目录的档位是单人判断**，没有第二意见，也没有使用反馈；国内资源覆盖薄于英文资源。
5. **docs 页面是设计类仓库的门面，却只经过了一轮自评**，没有外部评审。

## 可证伪条件

如果以下任一成立，说明套件设计有问题，应当修改而不是辩护：

- 用 `design-studio` 做同一个 brief 三次，三次的方向在"是否与主题无关"这个判据下都落在同一处。
- 引入套件后，agent 的产出在 `quality-rubric.md` 上由独立评审打分，并不高于不使用套件时。
- 真实使用中，子 skill 的路由经常选错，或一次任务需要加载超过四个文件才能开始。
- `link-check` 发现一个季度内失效的条目超过一成，而维护流程没能在一次迭代内修完。
- 用户反复需要的东西（某个学科、某类交付物）不在任何子 skill 的范围内。
